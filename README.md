# AI-агент подбора стажировок и junior-вакансий

CLI-агент для русскоязычных студентов и junior-кандидатов. Пользователь пишет
обычный карьерный запрос вроде `стажировка python москва`, агент сам решает,
как его разобрать, когда сходить во внешний API, как привести вакансии к
единой структуре, как их отранжировать и как коротко объяснить, почему именно
эти варианты попали в топ.

Проект честно комбинирует два трека:

- **Track A:** агент реально использует внешний API как инструмент — открытый
  API портала «Работа России» / Trudvsem.
- **Track C:** в репозитории лежат raw-данные, нормализованный JSON, источник
  данных и дата сбора.

## Быстрый запуск одной командой

```bash
python3 main.py "стажировка python москва" --top 5 --compare
```

Команда работает даже без API-ключей. Если сеть недоступна или live API не
отвечает, агент использует локальный кэш `data/jobs.json`. По умолчанию CLI
печатает компактный и структурированный вывод: краткую сводку по запросу,
плотные карточки вакансий и, при `--compare`, короткую сравнительную таблицу.

## Что делает агент

Поток работы такой:

1. Пользователь передаёт естественный запрос в CLI.
2. Агент превращает его в структурированный `UserQuery`.
3. Получает вакансии из API «Работа России» или из локального snapshot.
4. Нормализует данные к единой схеме `Job`.
5. Ранжирует вакансии по explainable scoring.
6. Генерирует объяснения, почему каждая вакансия подходит.
7. Печатает компактный результат в терминал.

Если включён `GROQ_API_KEY`, агент работает в LLM-режиме и сам выбирает
следующий инструмент. Если ключа нет, проект переключается на устойчивый
детерминированный fallback-пайплайн.

## LLM

Для LLM-части выбран **Groq API** с моделью `llama-3.3-70b-versatile`.

Groq используется для двух задач:

- структурный разбор пользовательского запроса через Function Calling;
- генерация коротких объяснений по уже найденным вакансиям.

Включение LLM-режима:

```bash
export GROQ_API_KEY="<ваш_groq_api_key>"
python3 main.py "я студент, хочу стажировку по питону удалённо"
```

Установка зависимостей для Groq:

```bash
python3 -m pip install -r requirements.txt
```

Можно также положить ключ в локальный `.env` рядом с проектом:

```bash
GROQ_API_KEY=...
GROQ_MODEL=llama-3.3-70b-versatile
```

`.env` добавлен в `.gitignore`, поэтому ключ не должен попасть в репозиторий.
Для полностью offline-проверки можно запустить:

```bash
LOAD_DOTENV=0 LIVE_API_ENABLED=0 python3 main.py "стажировка python москва"
```

## Источник данных

Основной источник — открытый API портала «Работа России»:

- API: `http://opendata.trudvsem.ru/api/v1/vacancies`
- Документация: `https://www.work-rus.com/opendata/api.html`
- Нормализованный датасет: `data/jobs.json`
- Raw snapshot: `data/raw/trudvsem_2026-04-23.json`
- Live snapshot последнего запуска tool: `data/raw/trudvsem_latest_2026-04-24.json`

Raw snapshot хранится без контактных полей работодателей. В нормализованной
схеме остаются только поля, действительно нужные агенту: название вакансии,
компания, локация, занятость, навыки, описание, зарплата, опыт, источник
и ссылка на карточку.

Практическая деталь: Trudvsem API иногда плохо ведёт себя на крупных ответах,
поэтому `fetch_jobs` запрашивает live-данные маленькими страницами по 3
вакансии (`TRUDVSEM_PAGE_SIZE=3`) и собирает до 12 результатов за один запрос
(`TRUDVSEM_LIMIT=12`). Это сохраняет реальный tool use и делает CLI заметно
стабильнее.

## Инструменты агента

Агент использует шесть инструментов через единый реестр `TOOLS` в [src/agent.py](/Users/glebgrigorev/Desktop/programming/LLM-helper_task/src/agent.py:15).

При этом в основном сценарии агент по сути опирается на два ключевых
инструмента:

- `parse_query` — чтобы понять, что именно пользователь ищет;
- `fetch_jobs` — чтобы реально сходить во внешний API и получить вакансии.

Это два минимально необходимых tool-вызова, без которых проект перестал бы быть
агентом в смысле задания. Но остальных инструментов здесь не «слишком много»,
а ровно столько, сколько нужно, чтобы поведение было осмысленным, разложимым на
шаги и проверяемым.

Почему шесть инструментов здесь оправданы:

- Если бы всё было слито в одну функцию вроде `find_jobs(query)`, LLM не могла
  бы принять ни одного промежуточного решения. Это был бы не агент, а просто
  один вызов функции.
- `parse_query` и `fetch_jobs` решают две принципиально разные задачи:
  понимание запроса и внешний HTTP-вызов. Их разделение уже даёт агенту право
  выбирать, когда и как искать.
- `filter_and_rank_jobs` отделён от `fetch_jobs`, потому что ранжирование —
  это детерминированное вычисление по правилам, а не LLM-действие. Из-за этого
  можно отдельно тестировать поиск и отдельно скоринг.
- `explain_top_jobs` идёт после ранжирования, потому что текстовое объяснение
  имеет смысл только по уже отобранным вакансиям.
- `compare_jobs` вообще не участвует в принятии решений агента: это отдельный
  форматирующий шаг по флагу `--compare`.
- `broaden_query` нужен для условного ветвления. Именно благодаря ему агент
  может увидеть, что live-результатов мало, и попробовать более широкий запрос,
  а не просто молча вернуть пустую выдачу.

Именно такое разбиение обычно считается нормальным для агентных систем: один
инструмент — одно атомарное действие. Это делает проект проще для логирования,
отладки, повторного запуска с конкретного шага и изолированного тестирования.

`parse_query` — [src/tools/parse_query.py](/Users/glebgrigorev/Desktop/programming/LLM-helper_task/src/tools/parse_query.py:1)  
Преобразует естественный запрос в `UserQuery`. В LLM-режиме использует Groq
Function Calling со строгой JSON-схемой. Без ключа переключается на
rule-based fallback по словарю русских и транслитерированных терминов.

`fetch_jobs` — [src/tools/fetch_jobs.py](/Users/glebgrigorev/Desktop/programming/LLM-helper_task/src/tools/fetch_jobs.py:1)  
Ходит в API «Работа России», нормализует ответ в `list[Job]` и сохраняет
очищенный raw snapshot. Если API недоступен, возвращает данные из
`data/jobs.json`.

`broaden_query` — [src/agent.py](/Users/glebgrigorev/Desktop/programming/LLM-helper_task/src/agent.py:39)  
Условный инструмент расширения запроса. Если live API вернул слишком мало
результатов, агент может запросить у LLM более широкий поисковый запрос или
применить rule-based fallback.

`filter_and_rank_jobs` — [src/tools/filter_and_rank.py](/Users/glebgrigorev/Desktop/programming/LLM-helper_task/src/tools/filter_and_rank.py:1)  
Explainable ranking по пяти сигналам:

| Сигнал | Вес | Что означает |
| --- | ---: | --- |
| `keyword_overlap` | 35% | совпадение навыков и технологий |
| `type_match` | 15% | совпадение занятости: полная или частичная |
| `location_match` | 15% | совпадение города или удалённого формата |
| `junior_fit` | 10% | подходит ли вакансия под уровень internship / junior |
| `role_alignment` | 25% | совпадение роли: backend, frontend, devops, data и т.д. |

Скорер убирает дубликаты, жёстко отсеивает senior/lead для junior-запросов и
мягко диверсифицирует топ, чтобы верх выдачи не был забит одним работодателем.

`explain_top_jobs` — [src/tools/explain_job.py](/Users/glebgrigorev/Desktop/programming/LLM-helper_task/src/tools/explain_job.py:1)  
Генерирует объяснение для каждой вакансии из топа. В текущей версии ответ Groq
сначала собирается целиком, а затем выводится аккуратно в итоговом CLI.
Без `GROQ_API_KEY` используется шаблонный fallback.

`compare_jobs` — [src/tools/compare_jobs.py](/Users/glebgrigorev/Desktop/programming/LLM-helper_task/src/tools/compare_jobs.py:1)  
Короткая сравнительная таблица по топ-N вакансиям. Вызывается только по флагу
`--compare`.

## Режимы работы

С `GROQ_API_KEY`:

- агент запускает **LLM-driven agentic loop**;
- модель сама решает, какой инструмент вызвать следующим;
- если live-результатов мало, может сама инициировать расширение запроса;
- после agentic loop есть защитное «добирание» обязательных шагов, чтобы CLI
  всегда вернул полный результат.

Без `GROQ_API_KEY`:

- запускается детерминированный pipeline;
- порядок жёстко задан:
  `parse_query -> fetch_jobs -> broaden_query? -> filter_and_rank_jobs -> explain_top_jobs`

## CLI

Актуальный интерфейс ориентирован не на декоративные таблицы, а на плотный
рабочий вывод:

- сверху идёт краткая сводка по запросу;
- дальше каждая вакансия печатается как компактная карточка:
  `уровень`, `занятость`, `где`, `совпало`, `почему`, `описание`, `ссылка`;
- `--compare` добавляет короткую строковую таблицу сравнения;
- `--verbose` включает техническую трассу агента;
- `--interactive` запускает REPL с накоплением истории запросов.

Примеры:

```bash
python3 main.py "стажировка python москва"
python3 main.py "junior backend python удалённо" --top 5 --compare
python3 main.py "стажер devops docker linux" --top 3
python3 main.py --interactive
python3 main.py "стажировка python москва" --verbose
```

## Ограничения

- Без `GROQ_API_KEY` понимание запроса остаётся rule-based, поэтому необычные
  формулировки распознаются хуже.
- Trudvsem содержит шумные и неполные карточки, поэтому качество ответа зависит
  от исходных данных.
- В API часто встречаются зарплаты вида `от 0`, поэтому зарплата не выступает
  главным сигналом ранжирования.
- Скоринг эвристический и объяснимый, но не обучен на реальной истории откликов.
- Live API может быть временно недоступен, поэтому локальный snapshot оставлен
  как часть штатного сценария проекта.
